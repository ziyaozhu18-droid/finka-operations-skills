# 提需检查备忘录

供“运营提需助手”在输出完整澄清卡前内部核对。它不是运营填写表，也不是固定追问清单：仅使用与当前需求有关的项；缺口应按其归属放入“运营需补充”“需产品确认”或“影响范围与风险”。

## 先判断：是否已经能交产品评估

- 运营要解决的具体问题、受影响的人群或场景是否明确？
- 本期触达入口、覆盖范围、频次或时效是否已知？
- 已知事实是否都能标出来源，且没有把方案或推断写成事实？
- 缺口是运营可以补充的业务事实，还是只能由产品决定的能力/规则？

若任一缺口会改变方案边界，保持“澄清中”，只问其中最关键的一题。

## 通用高频遗漏

| 核对项 | 需要确认的内容 | 常见落点 |
| --- | --- | --- |
| 目标与优先级 | 要改善什么；本期最重要的结果是什么；是否有明确时限 | 运营需补充 / 期望结果与优先级 |
| 触达与范围 | 现有入口、适用用户/城市、起止时间、频次、是否全量 | 运营需补充 / 需产品确认 |
| 基准与变化 | 当前流程是什么；希望改变哪一步；不受影响的规则是什么 | 已知事实 / 影响范围与风险 |
| 异常与撤销 | 到期、撤下、投诉、信息失效、误配置时谁处理、多久处理、如何恢复 | 风险 / 需产品确认 |
| 成功判断 | 当前能观察什么；哪些指标或归因需要新增能力 | 验收与数据观察建议 |
| 责任与依赖 | 运营、产品、后台产品、审核/风控或外部合作方各自要做什么 | 下一步与责任人 / 风险 |

## 配置、后台与人工流程

当需求涉及“可配置”“优先展示”“定期维护”“后台支持”时，核对：

- 配置的对象、适用入口和人群范围是什么；生效时间、默认值、优先级与上限是什么；
- 谁能操作，是否需要审核；误配、到期、取消或回滚如何处理；
- 当前是否已有可核验的承接能力；否则只能标为 `需后台产品评估`，不得设计字段或权限；
- 若用人工流程替代，运营具体如何发布、更新、撤下，响应时限和事实台账由谁维护。

翻咔一律遵循“无法发版”边界：新增端上/后台能力只作为后续选项，不能伪装成本期方案。

## 内容、活动与外部合作

当涉及内容推荐、活动、商家、社群或合作方时，核对：

- 内容或合作依据、展示字段、素材和公开授权是否齐全；
- 活动状态、报名/名额、城市/距离、已参与用户的展示是否受现有规则约束；
- 合作到期、闭店、投诉、取消或素材失效后的临时隐藏、核实、撤下与历史内容处理；
- 公开联系方式、位置、标签、敏感口径是否需要审核、风控或法务确认。

## 用户规则与体验闭环

当需求改变页面、名单、推荐、通知或跳转时，核对：

- 已报名/已加入、满额、下架、过期、角色变化等用户是否会看到不同结果；
- 注销、封禁、拉黑等异常账号在相关入口、列表、通知和跳转中如何处理；
- 若有 Push 或消息，是否说明触发、展示、落地页、失效和用户关闭后的回流；
- 页面或内容是否允许分享到站外；如允许，分享标题和分享描述是否已明确；
- 是否会与既有排序、推荐、城市、距离或状态规则冲突。

嗒哒仅可依据当前使用者有权读取、且已回读的原始 PRD 核验；无法核验时按主流程降级为“未发现依据”或 `需产品确认`。

## 维护原则

- 只把实际提需中反复出现、且会改变评估结论的遗漏沉淀到本文件。
- 一条只记录一个可判断的问题，避免堆砌泛泛提醒；若已有主流程约束，不重复抄写。
- 新增或调整后，用 `references/acceptance-cases.md` 补一个能观察到行为变化的用例。
